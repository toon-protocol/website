A price makes a route cost something. A settlement backend is what lets anyone actually pay it. There are two families of chain, EVM and Solana, and each has networks within it: Base and Robinhood Chain are EVM networks, Solana has devnet and mainnet-beta. A node may carry a table for any of them; with several, it accepts vouchers on all at once. Every channel is an x402 batch-settlement channel: on EVM that is x402's audited x402BatchSettlement contract, and on Solana the Solana Foundation's payment-channels program. Both are constants of the binary, the same address on every network, so there is nothing chain-specific to name beyond your own RPC, token and key.

The short version: add the eight-line settlement block below to connector.toml, give its key a little gas, and restart. connector init writes one for you, on any of six networks (Run a node lists the flags); the block below is the devnet one. The rest of this page is what each line commits you to.

The shape

StepWho actsWhat touches the chain
Termsclient readsNothing: GET /ilp, or the 402 greeting on an unpaid request.
OpenclientEVM: one deposit, relayed by an x402 facilitator. Solana: one open, co-signed by your node.
PayclientNothing: one signed voucher per paid packet, carried inside ILP.
Landyour nodeBatched claim + settle (EVM), settle (Solana), every ten minutes.
ExitclientEVM: initiateWithdraw, then finalizeWithdraw. Solana: request_close, then the payer's withdrawal.
Exit raceyour nodeLands its latest voucher as soon as it sees the exit start.

Value moves one way on a channel, client to you. Claims are frequent and free, and settlement is rare. The chain sees the deposit, the sweeps, and the exit.

The settlement block

connector.tomldevnet values

rpc_url               = "https://base-sepolia-rpc.publicnode.com"

decimals              = 6              # units per token: 6 means 1,000,000 = 1.00
asset_eip712_name     = "USDC"         # the token's own EIP-712 domain:
asset_eip712_version  = "2"            # cast call <token> 'name()(string)' / 'version()(string)'
# min_withdraw_delay_secs = 86400      # default one day; 900 at least, 30 days at most
# asset_transfer_method = "eip3009"    # "permit2" for a token without ERC-3009
# facilitator_url = "https://..."      # the x402 facilitator payers relay deposits through

[settlement.evm.key]
key_file = "/app/data/settlement.key"

# Solana, public devnet.
[settlement.solana]
rpc_url               = "https://api.devnet.solana.com"
token_address         = "34eSxY7qxQ4GzyhDJ8GpUcTz1WWzruGbJbR8q6TtxfQU"  # an SPL mint; Token-2022 is refused
decimals              = 6
min_sponsored_deposit = 1000000        # base units: the smallest deposit whose open you will pay rent for
# min_grace_period_secs = 86400        # default one day; 900 at least

[settlement.solana.key]
key_file = "/app/data/settlement-solana.key"

Copy the token address rather than picking your own: a voucher resolves against one token, so every node that might accept a given voucher has to name the same one. The two asset_eip712_* keys and min_sponsored_deposit have no default and are required wherever their table exists. Read the EIP-712 name and version off the token itself: Base mainnet's native USDC is "USD Coin" / "2", not "USDC". A wrong name shows up only as every client's deposit failing.

decimals is what turns a price into money. The node reads the token's own decimals at boot and refuses to start if the config disagrees, because a wrong value misprices every route by a factor of ten or more. Every other settlement value is verified against the chain the same way, which is why there is no --network flag: which chain a node is on is these values. The node confirms x402BatchSettlement's code is present at its fixed address before it will serve.

This page does not state either faucet's limits: Robinhood's refused an automated read when this was written, so its current terms are unconfirmed, and Arbitrum's post is from the testnet's launch. Check both before you rely on them.

No TOON faucet or facilitator serves Robinhood Chain. A payer needs its own ETH to open a channel. toon-client faucet serves only Base Sepolia and Solana devnet, and toon-client's EVM presets name only 84532, so paying on Robinhood Chain has not been run.

USDG is not USDC. There is no Circle USDC on this chain. Its dollar is Paxos's USDG, so copy these values rather than Base's: boot refuses Base's domain on this token, by name. USDG's domain is one you can't look up by asking: its version() call reverts, so you must copy it. The version is known only because "Global Dollar" and "1" hash to its DOMAIN_SEPARATOR(). Prices count USDG's base units, so price = 1000 is 0.001 USDG.

A peering needs the same token at both ends. Your counterparty needs a table on this token on this network, or opening the channel fails with TokenNotShared.

USDG and USDC are not interchangeable, and the binary will not notice if you treat them so. A node with no [[tokens]] forwards between a USDG table and a USDC table at par without complaint: both have 6 decimals, so the two boot and forward unconverted, whatever a dollar on either side is worth to you. Declaring [[tokens]] for both, and a rate for the pair, is how to prevent it; the rate is demanded only once you declare tokens.

What you are trusting, as L2BEAT and Robinhood's terms stated it on 2026-11-02. Weigh it when you decide how much to hold here, and re-read both, since these facts change faster than this page:

  • One sequencer, run by Robinhood. A voucher is worth what you can land, and landing it goes through that sequencer.
  • Below Stage 0. L2BEAT rates the chain "not even a Stage 0 project". Only two whitelisted actors can submit fraud proofs.
  • Instant upgrades. A 7-of-8 multisig can upgrade core contracts with no delay, so L2BEAT gives users no exit window. It reaches the chain beneath x402BatchSettlement, not that contract, which is immutable.
  • A transaction filter that defeats forced inclusion. An authorised filterer can register a transaction hash, and that transaction then fails, even when it was force-included from L1, so L2BEAT calls forced inclusion "not a reliable censorship escape hatch".
  • Address blocking. Robinhood reserves the right to restrict or block specific wallet addresses from the chain.
  • The issuer. Paxos can freeze or pause USDG, and the token is upgradeable. Circle can do the same to USDC on Base and Solana, so this risk isn't peculiar to this chain. A freeze of x402BatchSettlement, or a pause of the token, stops payouts on every channel in that token at once.
Before you set rpc_via_socks_proxy on this table, read Robinhood's terms. They bar using a VPN, proxy or other tool to mask your identity, location or IP address.

How far this has been run. x402's contracts here match Base's except for their chain id and domain separator. An unmodified node has booted on both public RPCs and run a whole channel's life in USDG on a local fork of mainnet, not through the live sequencer. Nobody has yet sent a transaction through the live sequencer from this binary, run the shipped image on this chain, or paid from toon-client.

How a channel is admitted

You do not list the channels your payers will use, and you could not: a client's channel does not exist until that client opens it toward you. A voucher naming a channel you have never heard of is resolved from chain and admitted, which is what makes paying you permissionless rather than an arrangement. Your node only admits a channel whose terms are the ones it published:

ChainThe channel must have
EVMreceiver and receiverAuthorizer = your settlement address; token = your token_address; withdrawDelay ≥ your minimum; a nonzero payerAuthorizer. That last rule is stricter than x402. The client's deposit is relayed by the facilitator you name; a payer holding ETH can deposit directly instead. The first voucher on a channel your node has not seen carries the full channelConfig.
SolanaThe client builds an open in which your settlement key is fee payer, rent_payer and payee, signs it, and posts it to POST /ilp/batch-settlement/solana/open, which the greeting names as extra.sponsorEndpoint. The node checks every field, co-signs, submits, waits for confirmation, and admits it. The endpoint is public, bounded by a cap of 8 sponsorships in flight, 1 per payer, and an hourly budget of failed opens. Only SPL Token mints; Token-2022 is refused.

How a voucher is checked. A voucher has no nonce. It is accepted only if its amount is strictly greater than the last one accepted on that channel, by at least the route's charge. A replayed voucher buys nothing. A packet to a free route carries no voucher at all. A client that lost track asks POST /ilp/claim-state to learn the amount it has to beat.

How you get paid

Automatically, with no operator write, for what lands on chain:

ChainCadence
EVMEvery 5 s, read new WithdrawInitiated logs and claim that channel's latest voucher at once, because only the amount already claimed survives the withdrawal. Every 10 min, claim every held voucher above what the chain records, many channels in one transaction, then settle to your address. The sweep also runs at boot.
SolanaEvery 10 s, rediscover every channel you sponsored from the chain. Open: settle the latest voucher every 10 min. Closing: settle_and_seal inside the grace period. Sealed: distribute. Distributed: reclaim the channel's rent.

The one-day default minimum for withdrawDelay and grace_period is the window a delayed or censored landing transaction still has. POST /channels/:id/land is the manual lever for planned maintenance.

Who pays gas, and why

x402BatchSettlement has no fee field. Nothing on chain pays a facilitator, so gas is paid by whoever wants the transaction to happen. In TOON that is the seller: your node names the facilitator it relays deposits through, and deposit gas is a cost of the sale. Your node publishes that URL and never calls it; the payer does.

StepWho pays
EVM deposit or top-upThe facilitator you name, off chain at your expense; or the payer, from its own ETH.
EVM Permit2 approval (once)The facilitator, if it sponsors approvals for this token; otherwise the payer's own ETH.
Solana openYou: the transaction fee and 4,711,920 lamports (about 0.0047 SOL) of rent per channel, returned at reclaim.
A voucherNobody: a signature.
EVM claim and settleYou, from the EVM settlement key's ETH.
Solana settle, seal, distribute, reclaimYou, from the Solana settlement key's SOL.
The payer's exitThe payer.
Your own outbound channelsYou: when your node pays a peer, it deposits directly and pays its own gas.

Choosing a facilitator

The facilitator must never be your receiverAuthorizer. That key can refund to the payer anything you have earned and not yet claimed. Your node always names its own settlement address, so a facilitator that advertises its own authorizer is simply not used as one.
  • Run a stock x402 facilitator yourself. TOON's Onboarder is one; the devnet runs it at onboard.devnet.toonprotocol.dev. It is the published @x402/evm facilitator with no receiverAuthorizer. Its gas key needs ETH, and that ETH is the cost of sale.
  • Use a hosted one. Several hosted x402 facilitators serve Base mainnet. Check that the one you pick lets you keep your own receiver authorizer, and check its current terms with the provider.
  • Name none. Then only a payer that brings its own facilitator, or holds ETH, can deposit. The client falls back, in order, to the payer's own facilitator, then yours, then the devnet Onboarder on Base Sepolia only.

Solana needs none of this. The payer posts its open to your sponsor endpoint, and your node is the fee payer.

Checking it

curl -s https://your-node.example/ilp | jq '.batchSettlements, .voucherSigners'

Check that there is one batchSettlements entry per chain you configured, with your settlement address as payTo (EVM) or your key as feePayer (Solana), and the name, version, assetTransferMethod and facilitator you meant to publish. After a client has paid, read the journal with your bearer token:

curl -s -H "Authorization: Bearer $TOKEN" https://your-node.example/claims | jq

Each paying channel shows "scheme": "batch-settlement" and a cumulative_amount that rises with every packet. Watch that watermark, not the count of claims.

Before you rely on it

Fund the settlement key before you start the node, and know that booting a config is not a dry run. A Solana backend submits a real transaction at connect; with no gas the connector exits on a chain error that reads like a config bug. With a funded key, starting a node "just to see whether the TOML parses" spends real money.
  • One way per channel. To pay a client back, open a channel of your own toward the terms it publishes (POST /channels).
  • Solana costs SOL. Each sponsored channel locks about 0.0047 SOL of rent until reclaimed. Your node's token account for the mint must already exist.
  • Third-party code. The EVM contract is ownerless and immutable; nothing can rescue an escrow that USDC's blacklist has frozen. payment-channels can be upgraded, on mainnet-beta by a 3-of-5 multisig with no time lock. What you risk as a receiver is whatever you have accepted in vouchers and not yet landed on chain.
  • An ILP outcome is never an HTTP one. A FULFILL and a REJECT both come back at HTTP 200. A caller with no voucher on a priced route gets 402 with the greeting.
